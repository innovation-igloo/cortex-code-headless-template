How the craft is built

The template is a thin, production-shaped wrapper around the Cortex Code Agent SDK. This is the map of its parts and how a single request travels through them.

The stack

Six layers, one service

Each layer has one job. The SDK does not call a Snowflake API directly; it drives the cortex CLI, which runs the actual agent loop.

LayerFileResponsibility
HTTPserver.pyFastAPI app: /health, /ready, POST /chat (SSE), session routes.
Agentagent.pyWraps the SDK client: builds options, owns one long-lived session per session_id, normalizes messages into SSE events.
Authauth.pyWrites the CLI connection file (config.toml) and inference connection (cortex/settings.json) from env/secret.
Toolstools.pyExample in-process MCP tool (the Python-only extension point).
Policypermissions.py, hooks.pyTool allow/deny policy and lifecycle audit hooks.
RuntimeDockerfile, entrypoint.shShips the cortex CLI + app; launches uvicorn (--loop asyncio).
Two things the SDK does not do for you
The cortex CLI is a required binary the SDK spawns; it is not bundled, so the image installs it. And the CLI reads its connection from a file, not from SNOWFLAKE_CONNECTIONS_* env vars, so auth.py writes that file at startup.
The lifecycle

What happens on a request

  1. Client POST /chat with a prompt and session_id.
  2. SPCS ingress authenticates the caller and forwards to the container on port 8000.
  3. server.py gets or creates a long-lived agent session (one CLI subprocess), reused across turns for context.
  4. The SDK writes the prompt to the CLI; the CLI runs the loop against Cortex, calling tools as needed.
  5. Assistant text, tool calls, and the final result are normalized to data: {...} SSE frames and streamed to the client.
Two different logins

Don't confuse the two auth directions

Most of the deployment pain comes from conflating these. They are separate doors with separate keys.

Client → service (ingress)

How an external caller reaches the public endpoint. Uses the SPCS ingress OAuth flow (send a PAT as Snowflake Token="..." and follow the redirect with a cookie jar). Covered in Launch.

Service → Snowflake (inference)

How the agent, once running, authenticates to Cortex. This is the hard one in SPCS and has its own page: Pre-Flight Checks.

Long-lived sessions
One CortexCodeSDKClient (and one CLI subprocess) is held per session_id, not per request, so multi-turn context is preserved and you don't pay subprocess spawn + version-check + initialize on every call.
